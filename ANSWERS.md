# Контрольные вопросы по лекции 52

1. **Что такое CSS и для чего он используется?** Язык таблиц стилей: задаёт оформление, расположение элементов и адаптивность HTML-страницы.
2. **Что такое автоматическая проверка CSS?** Анализ исходного CSS инструментом по настроенным правилам без ручного поиска каждой ошибки.
3. **Какие ошибки бывают в CSS?** Опечатки в свойствах, неверные цвета и значения, синтаксические ошибки, дубли свойств и нарушения соглашений.
4. **Что такое линтер?** Инструмент статического анализа кода, который сообщает о нарушениях заданных правил.
5. **Для чего нужен Stylelint?** Для обнаружения ошибок CSS и контроля выбранных правил качества.
6. **Чем Stylelint отличается от HTML-валидатора?** Stylelint анализирует стили; HTML-валидатор — разметку и структуру HTML.
7. **Какие правила можно настроить?** В работе включены проверка HEX-цветов, запрет дублей свойств внутри блока и обнаружение неизвестных свойств. Другие проверки требуют дополнительных правил.
8. **Для чего нужен .stylelintrc.json?** Хранит конфигурацию Stylelint и набор правил проекта.
9. **Что делает npm install --save-dev stylelint?** Устанавливает Stylelint как зависимость разработки, обновляет package.json и package-lock.json.
10. **Что делает npx stylelint "**/*.css"?** Запускает локальный Stylelint для CSS-файлов в корне и вложенных папках; node_modules по умолчанию исключён.
11. **Какова роль GitHub Actions?** Автоматически получает код, готовит Node.js, устанавливает пакеты и запускает Stylelint при заданном событии.
12. **Где размещают YAML Workflow?** В .github/workflows; в работе — css-check.yml.
13. **Для чего checkout и setup-node?** checkout получает файлы репозитория, setup-node настраивает Node.js и npm на runner. В работе использованы версии v7 вместо v4 из примера.
14. **Зачем устанавливать зависимости перед проверкой?** На новом runner ещё нет локального Stylelint. npm ci устанавливает версии из lock-файла.
15. **Что произойдёт при ошибке Stylelint?** Он выведет файл, строку и правило; при нарушениях правил вернёт код 2, шаг и workflow завершатся Failure.
16. **Где посмотреть результат?** GitHub → репозиторий → Actions → CSS Validation → css-check → Check CSS.
17. **Почему важны единые правила в команде?** Все изменения проверяются одинаково, что снижает число ошибок и разногласий при проверке кода.
18. **Гарантирует ли успех правильное отображение сайта?** Нет. Он подтверждает только прохождение включённых правил. Нужна отдельная проверка в браузере на разных размерах экрана.
